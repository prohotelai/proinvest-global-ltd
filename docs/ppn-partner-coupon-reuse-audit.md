# PPN Partner Coupon Reuse Audit

## 1. Executive Verdict
- **Can PPN become source of truth for partner coupon identity?** **Yes, partially with minimal extension.**
  - PPN already has a globally unique partner identity token (`Partner.partnerCode`) used across referral links and product event attribution (`ppn_ref`).
  - PPN already has first-class products and partner-product relationship surfaces (especially `PartnerCommissionOverride`), but does **not** have a coupon/promo model.
- **Reusable building blocks already exist?** **Yes.**
  - Reusable partner code identity, product registry, signed product-authenticated ingest API, and admin UIs for partner/product management are implemented.
- **Smallest viable reuse path (without redesign):**
  - Reuse `partnerCode` as canonical coupon identity seed in PPN, and store product-specific coupon override per partner-product only where needed (missing today, would need one field/table extension).
  - Downstream products can already pass/resolve `ppn_ref` through existing signed event flows; PPN can act as origin for identity values once one retrieval/sync path is added.

## 2. Current Partner Data Model
### Partner identity fields
- `Partner.id` (UUID PK) and `Partner.userId` (unique FK) identify a partner internally.
- `Partner.partnerCode` is a unique external code and is explicitly documented as the referral code.
- `Partner.type`, `status`, `tierId`, geo controls, and application profile fields are present.

### Referral/tracking fields
- Referral identity used in traffic/events is `ppn_ref`, and event handlers resolve this to `Partner.partnerCode`.
- Partner links are generated by appending `ppn_ref=<partnerCode>` to product URLs.
- Redirect endpoint `/api/v1/ppn/r/[partner_code]` resolves partner+product and redirects with `ppn_ref` query param.

### Commission-related fields
- Commission attribution stack: `Click`, `Attribution`, `CommissionEntry`, `LedgerTransaction`.
- Partner/product(+plan) commission relationship is modeled in `PartnerCommissionOverride`.

### Existing code fields relevant to coupon identity
- **Exists:** `Partner.partnerCode` (global unique partner code).
- **Not implemented:** dedicated `couponCode`, `promoCode`, `discountCode`, or offer/campaign code entity in schema.
- Natural current storage candidate for partner-specific coupon identity:
  - Global: `Partner.partnerCode` (already unique and externally used)
  - Product-specific: partner-product join area via `PartnerCommissionOverride` (structure exists but only stores commission percent settings)

## 3. Current Product Model
- Products are first-class records in `Product` with `id`, `name`, `slug` (unique), `domain`, `status`, `webhookSecret`, and landing/pricing URLs.
- Product plans are first-class in `ProductPlan` with unique composite (`productId`, `planKey`, `billingCycle`).
- Partner/product relationships already exist indirectly through:
  - `PartnerCommissionOverride` (`partnerId`, `productId`, optional `planId`)
  - `Click`, `Attribution`, `CommissionEntry` linking partner and product behaviorally.
- Product metadata is sufficient for product-specific behavior routing (slug/domain/status/secret).
- **Could one partner have different coupon codes per product today?**
  - **Not implemented directly.**
  - Structural insertion point exists (partner-product relation surface), but there is no coupon field.

## 4. Existing Coupon/Promo/Discount-Like Features
### What exists
- Referral/tracking code system: `partnerCode` / `ppn_ref`.
- UTM campaign string capture in click payload (`utm.campaign`) and stored as serialized `Click.utm`.
- Invoice schema carries `discount_amount`, but this is an input amount from downstream billing events (not a managed coupon model in PPN).

### What does not exist
- **Not implemented:** coupon master records, promo codes, voucher tables, offer/campaign management entities, discount rules engine, redemption tracking, coupon validity windows, per-product coupon catalogs.
- **Not implemented:** admin UI specifically for coupon/promo/discount lifecycle.

### Similar-enough reusable pieces
- `partnerCode` already serves as stable external token and can be reused as coupon identity basis.
- Partner/product admin surfaces and APIs can be extended with minimal UI/API shape changes.

## 5. Existing Integration / Sync Capabilities
### Existing APIs
- Inbound signed event ingestion (`/api/v1/ppn/events/*`) with product identity + HMAC verification.
- Redirect helper for referral links (`/api/v1/ppn/r/[partner_code]`).
- Partner portal APIs (`/partner/dashboard`, `/partner/links`, `/partner/commissions`, etc.) auth-gated.
- Admin APIs for products/partners/commissions/assets/settings.

### Existing sync / signed patterns
- Security model is product-authenticated inbound push to PPN:
  - Product identified by ID or slug.
  - Signature validated with product `webhookSecret`.
  - Timestamp replay protection + idempotency log.
- This is robust for downstream->PPN event sync.

### What VisaRiskAI could realistically consume today
- VisaRiskAI can send events with `ppn_ref` and `product_slug` over signed APIs.
- VisaRiskAI can rely on PPN for partner attribution resolution by partner code.
- **Not implemented today:** a documented public/signed endpoint for downstream products to fetch partner metadata/coupon mappings from PPN.
- **Not implemented today:** outbound webhooks/push from PPN to downstream products.

## 6. Best Reuse Opportunities
Ranked least invasive -> most invasive.

1. **Reuse `Partner.partnerCode` directly as coupon identity**
   - Reuse: existing unique partner code and existing `ppn_ref` flows.
   - Why attractive: zero new data model required for global partner coupon identity.
   - Still needed: product-side agreement that coupon code == partnerCode (normalization/validation), and optional lookup API if product needs metadata beyond the code.

2. **Add one product-specific coupon field on existing partner-product relation surface**
   - Reuse: `PartnerCommissionOverride` as current partner-product anchor.
   - Why attractive: avoids introducing a broad campaign system; leverages existing admin/product scoping.
   - Still needed: schema field + admin/API exposure + uniqueness constraints per product as required.

3. **Introduce dedicated partner-product coupon mapping entity**
   - Reuse: existing `Partner` and `Product` primary entities and admin auth patterns.
   - Why attractive: clean separation from commission configuration semantics.
   - Still needed: new model, CRUD endpoints/UI, validation, and downstream fetch contract.

4. **Full promo/campaign subsystem**
   - Reuse: existing auth/admin/product primitives only.
   - Why attractive: long-term flexibility.
   - Still needed: substantial net-new design and implementation (currently absent).

## 7. What Is Missing
Only missing pieces observed in repo:
- Dedicated coupon/promo/discount domain model in DB (**not implemented**).
- Coupon management admin/API surfaces (**not implemented**).
- Downstream-readable partner coupon metadata endpoint (product-auth or service-auth) (**not implemented**).
- PPN outbound sync/webhook for partner metadata propagation (**not implemented**).
- Explicit per-product partner coupon override storage (**not implemented**).

## 8. Minimum Viable Path
If coupon identity must originate from PPN with least effort:
1. Treat `Partner.partnerCode` as canonical coupon identity in PPN immediately.
2. Keep downstream products consuming this as `ppn_ref`/coupon basis (same identity), avoiding parallel manual identity stores.
3. Add only one minimal product-specific override store if business requires different codes per product; otherwise defer.
4. Add one minimal downstream-consumable lookup endpoint for partner code -> canonical coupon identity (+ optional product override) using existing product-auth signature pattern.

This path maximizes reuse of existing partner code identity, product registry, and signed integration model while avoiding a full coupon platform build.

## 9. Bottom Line
PPN already has the hard parts for identity, product scoping, and secure integration, but it does **not** currently implement coupons as a first-class concept. If the immediate goal is to stop per-product manual identity drift, moving coupon identity ownership to PPN is practical now by reusing `partnerCode` as canonical identity and adding only the thinnest retrieval/override layer. Keeping coupon identity fully product-local will continue duplication because the shared canonical partner code infrastructure already exists in PPN.
